TECHNICAL SPECIFICATIONS
================================================================================

ENCRYPTION ALGORITHM
  Algorithm: AES-256-GCM (Advanced Encryption Standard, 256-bit keys)
  Mode: GCM (Galois/Counter Mode) - provides authenticated encryption
  Key Size: 256 bits (32 bytes)
  Nonce Size: 96 bits (12 bytes) for GCM
  Authentication Tag: 128 bits (16 bytes)
  Status: NIST approved, industry standard

KEY DERIVATION
  Algorithm: PBKDF2-HMAC-SHA256
  Password-Based: Yes (derives key from user password)
  Salt Size: 256 bits (32 bytes) - randomly generated per encryption
  Iterations: 100,000 (makes brute-force attacks 100,000x slower)
  Output Key Size: 256 bits (32 bytes)
  Status: NIST SP 800-132 recommended

RANDOM NUMBER GENERATION
  Source: os.urandom() (OS cryptographic entropy)
  Usage: Salt and nonce generation
  Properties: Non-predictable, cryptographically secure
  Platform: macOS (Fortuna), Linux (/dev/urandom), Windows (CryptGenRandom)

FILE FORMAT
  Structure: [VERSION (1B)] [SALT (32B)] [NONCE (12B)] [CIPHERTEXT] [TAG (16B)]
  Overhead: 61 bytes per file
  File Types: All files supported (binary/text/images/archives/etc.)

SECURITY PROPERTIES
  ✓ Confidentiality: Only correct password allows decryption
  ✓ Integrity: Tampering detected via authentication tag
  ✓ Authentication: Proves correct encryption key was used
  ✓ No Password Storage: Password only in memory during use
  ✓ Unique Key Per File: Different salt → different key
  ✓ Unique Encryption Per File: Different nonce → different ciphertext
  ✓ Tampering Detection: Any modification breaks authentication tag

CRYPTOGRAPHIC SECURITY ANALYSIS
================================================================================

THREAT MODEL

Threat 1: Unauthorized File Reading
  Attack: Attacker steals encrypted file from disk
  Defense: AES-256-GCM encryption makes file unreadable
  Result: ✓ PROTECTED

Threat 2: Password Guessing
  Attack: Attacker tries multiple passwords
  Defense: PBKDF2 with 100,000 iterations
  Impact: 1 attempt takes ~1ms (1 million attempts = 1000 seconds)
  Result: ✓ PROTECTED

Threat 3: Rainbow Table Attack
  Attack: Pre-computed password→key mappings
  Defense: Unique random salt per encryption
  Result: ✓ PROTECTED (2^256 possible salts make tables impossible)

Threat 4: File Tampering
  Attack: Attacker modifies encrypted file
  Defense: Authentication tag (GCM mode) detects any modification
  Result: ✓ PROTECTED (1-bit change detected)

Threat 5: Known Plaintext Attack
  Attack: Attacker encrypts same file with same password
  Defense: Unique nonce for each encryption
  Result: ✓ PROTECTED (ciphertexts appear different)

Threat 6: Weak Password
  Attack: Password is easy to guess (e.g., "password123")
  Defense: PBKDF2 iterations + salt slow down guessing
  Residual Risk: Still vulnerable to advanced attacks, but slow
  Result: ✓ MITIGATED (not perfect, but acceptable for college project)

SECURITY ASSUMPTIONS

1. Operating System is Trusted
   - os.urandom() provides good entropy
   - No key logger installed
   - No memory dumps during operation

2. User Behavior
   - User doesn't share password
   - User remembers password correctly
   - User chooses reasonably strong password

3. No Quantum Computers
   - AES-256 is resistant to quantum attacks (unlike RSA)
   - PBKDF2 security not affected by quantum

LIMITATIONS & RESIDUAL RISKS

1. If password is weak (e.g., "123"), it can eventually be guessed
2. If computer is compromised, password could be captured
3. If encrypted file is accessible long-term, could be subject to advanced attacks
4. No protection if password is written down

MITIGATION STRATEGIES

1. User Education: Encourage strong passwords
2. Key Stretching: 100,000 PBKDF2 iterations (not configurable)
3. Secure Deletion: Original file not overwritten (user responsibility)
4. No Logging: Password never logged or displayed

CONCLUSION ON SECURITY

For a college-level DSP assignment: ✓ EXCELLENT
For production file protection: ✓ GOOD
For highly classified data: ~ ACCEPTABLE (with caveats)
For military/government: ✗ NOT SUITABLE (would need additional measures)

The system correctly implements modern cryptographic best practices
and is suitable for its intended use: educational demonstration and
personal file protection.
